# iTestAgent 全量用户故事与验收标准规格书

## 文档目的

本规格书把产品能力拆解为**可执行、可验收的用户故事（User Story）与验收标准（Acceptance Criteria）**，用于指导开发、测试和验收。

- 面向对象：产品、研发、QA
- 产品定位：Local-first、TUI-first、真机与 iOS Simulator 同级支持的测试 Agent
- 目标用户：iOS 客户端开发者本地自测与失败复现
- 参考验证项目示例：无既有测试、需自动构建签名的 iOS 项目

## 用语与约定

```
US-x.y     用户故事编号
AC         验收标准（Acceptance Criteria）
Given/When/Then  场景化验收写法
MVP        第一版必做
Deferred   推迟到后续版本
Experimental 实验性能力，标注后可交付但不作为硬门槛
```

优先级定义：

```
P0  MVP 硬门槛，缺失则第一版不可交付
P1  MVP 应做，允许有已知限制
P2  增强项，可推迟
```

## E1 安装与环境诊断（doctor）

### US-1.1 安装 CLI（P0）

作为 iOS 开发者，我希望能快速安装 iTestAgent CLI，以便在本机使用。

验收标准：

```
AC1 支持通过 npm 或 Homebrew 安装 itestagent
AC2 安装后 itestagent --version 能输出版本号
AC3 安装不要求登录任何账号
```

### US-1.2 环境诊断（P0）

作为开发者，我希望运行 itestagent doctor 就能知道本机能否跑真机测试。

验收标准：

```
Given 本机已安装 itestagent
When 运行 itestagent doctor
Then 检查并逐项报告：Xcode / Command Line Tools / xcodebuild / xcrun devicectl / xcrun xctrace / xcresulttool / Appium / Appium XCUITest Driver / WebDriverAgent 可构建可签名 / 证书与 provisioning profile / iPhone 连接 / Developer Mode / 设备信任 / WDA 启动与端口转发
AC1 每一项给出 通过 / 失败 / 需手动处理 三态
AC2 失败项给出可执行的修复指引（命令或手机端操作步骤）
AC3 不因单项失败而中断整体诊断，输出完整清单
AC4 诊断结果可被 engine 读取用于阻止不满足前置条件的执行
```

### US-1.3 首次真机跑通引导（P0）

作为首次使用者，我希望 doctor 能引导我完成签名、Developer Mode、设备信任、backend 前置条件配置。

验收标准：

```
AC1 doctor 能识别“签名不可用 / Developer Mode 未开 / 设备未信任 / backend 未就绪”并分别引导
AC2 引导为分步骤、可复制命令 + 手机端操作说明
AC3 明确告知首次跑通可能需要用户配合 15-30 分钟
AC4 引导完成后可复检并显示已通过
```

## E2 设备发现与真机准备（含 Simulator）

### US-2.1 列出本机设备（P0）

作为开发者，我希望运行 itestagent devices 看到本机连接的 iPhone。

验收标准：

```
Given 至少一台 iPhone 通过 USB 连接
When 运行 itestagent devices
Then 列出每台设备的 名称 / 型号 / iOS 版本 / UDID / 电量 / 状态
AC1 状态至少区分 healthy / untrusted / busy / developer_mode_off
AC2 无设备时给出明确提示与连接指引
AC3 数据来源使用 xcrun devicectl list devices
AC4 设备发现必须区分成功但无设备、部分成功与发现失败；失败或部分失败必须显式返回原因，不得把命令/解析失败静默表示为无设备
AC5 discovered 仅表示设备进入清单，ready 表示当前可作为执行目标；Simulator 只有 booted 才是 ready，shutdown/booting/shutting_down 等状态不得显示为 healthy
```

### US-2.2 设备健康检查（P1）

作为开发者，我希望执行前 Agent 能确认设备可用。

验收标准：

```
AC1 执行前自动 healthcheck：连接、信任、Developer Mode（physical）、backend 可用、runtime/simctl（simulator）
AC2 不满足时不进入执行，给出原因和修复建议（区分 physical/simulator 原因）
AC3 healthcheck 结果记录到 run metadata（含 targetKind）
```

### US-2.3 选择执行目标 — 真机与 Simulator（P0，ADR-011）

**作为** iOS 开发者，**我希望**在 CLI/TUI 中同时看到本机 iPhone 真机和可用的 iOS Simulator，**以便**根据当前需求选择执行目标。

验收标准：

```
AC1 itestagent devices 同时列出真机（devicectl）和 Simulator（simctl list --json）
AC2 每个设备显示 KIND（physical/simulator）、NAME、OS/RUNTIME、UDID、STATE
AC3 TestPlan 中 device 字段必须包含 targetKind（physical|simulator）
AC4 跨 targetKind 切换需要用户确认（不能静默 fallback）
AC5 不支持的目标类型标记为 blocked，给出原因
```

## E3 项目分析与 Project Profile

### US-3.1 全量项目扫描（P0）

作为开发者，我希望 Agent 启动后先全量扫描并理解我的项目。

验收标准：

```
Given 在 iOS 项目目录中启动 itestagent
When Agent 完成项目分析
Then 扫描 源码结构（View/ViewController/SwiftUI View/ViewModel/Router/Coordinator/Deep Link/feature modules）、文案资源、埋点名、网络 API 名、README/docs/注释、已有测试与 scheme/test plan
AC1 工程结构识别使用 XcodeProj + xcodebuild -list/-showBuildSettings，结果确定可靠
AC2 Swift/ObjC 源码分析采用分层能力：tier 1 静态扫描只能输出带 evidence+confidence 的候选事实；SwiftSyntax 是首选 tier 2 结构增强；sourcekit-lsp/SourceKitten 仅在已有可用 build/index 时作为 tier 3 语义增强。分析结果必须显式标注 analysisTier、已启用能力与 limitations，增强不可用不得阻塞项目分析或 TUI 启动
AC3 默认不读取 .gitignore 命中项、secrets、DerivedData 等敏感/无关文件
AC4 分析结果生成 Project Profile
```

### US-3.2 生成 Project Profile（P0）

作为开发者，我希望分析结果沉淀为结构化 Project Profile。

验收标准：

```
AC1 Project Profile 至少包含 app(name/bundleId/workspace/scheme)、features、testAssets、suggestedSmoke
AC2 默认存储 ~/.itestagent/projects/<project-hash>/project-profile.json
AC3 仅在用户确认“固化到项目”后写入 <project>/.itestagent/project-profile.json
AC4 Profile 可被 TestPlan 引用
```

### US-3.3 带证据的候选核心链路（P1）

作为开发者，我希望 Agent 给出候选核心链路，但由我确认，而不是自动断定。

验收标准：

```
AC1 Agent 输出“候选核心链路 + 置信度 + 证据来源”（如 README 第X节 / LoginViewController / 文案“下单” / 埋点 checkout_click）
AC2 在 TUI 中用户可勾选、排序、修正候选链路
AC3 只有用户确认的链路进入 TestPlan 和 Flow
AC4 系统不把未确认的推断链路当作既定事实
```

## E4 TUI 交互与 Agent 会话

### US-4.1 进入 TUI（P0）

作为开发者，我希望运行 itestagent 直接进入交互式 TUI。

验收标准：

```
AC1 itestagent 无参数时进入 OpenTUI 交互式界面
AC2 TUI 显示当前 workspace、设备状态、可输入自然语言
AC3 CLI 子命令（doctor/devices/config/--version）作为轻量辅助入口存在
AC4 TUI 的设备状态必须来自生产会话返回的 discovery status 与 ready target，不得仅以设备清单非空推断 healthy；部分发现显示 degraded，发现失败或只有未就绪设备显示 unavailable
```

### US-4.2 自然语言驱动（P0）

作为开发者，我希望用自然语言下达测试目标。

验收标准：

```
Given 已进入 TUI 且项目分析完成
When 我输入“帮我用本机 iPhone 跑一下登录 smoke 并分析失败原因”
Then Agent 理解意图并生成 TestPlan
AC1 支持多轮对话与追问
AC2 流式展示 Agent 思考、工具调用、执行进度
AC3 同一测试目标的多轮消息属于同一个 Agent Session / Test Run Session；普通追问不得隐式启动新规划或使已确认 TestPlan 失效
AC4 新测试目标必须由用户显式发起（第一版 TUI 使用 `/plan <test goal>`）；进入新规划周期时必须原子清除上一周期的 Intent、候选和草稿状态
```

### US-4.3 本地 Server 支撑长任务（P0）

作为开发者，我希望长任务、日志流、截图流稳定运行。

验收标准：

```
AC1 第一版具备本地 server，管理长任务、事件流、session 状态
AC2 TUI 作为 client 通过事件流订阅进度
AC3 子进程（xcodebuild/appium/xctrace）异常退出能被回收，不留僵尸进程
```

## E5 TestPlan 生成与确认

### US-5.1 编译 TestPlan（P0）

作为开发者，我希望自然语言最终变成结构化 TestPlan。

验收标准：

```
AC1 自然语言、TUI 操作、CLI 辅助命令都编译为统一 TestPlan
AC2 TestPlan 至少包含 target/device(targetKind+selector)/appSource/execution/features/testData/assertion/flows/metrics/performance(baselineDomain)/artifacts/report
AC3 TestPlan 可审计、可复现、可重跑
AC4 TestPlan 引用 Project Profile
```

### US-5.2 展示计划并确认（P0）

作为开发者，我希望执行前看到并确认计划。

验收标准：

```
Given Agent 生成了 TestPlan
When 展示给用户
Then 显示设备、执行方式、用例/链路、采集项、基线、预计耗时
AC1 提供 开始 / 修改 / 取消
AC2 用户可用自然语言修改计划（如“只跑登录，不要下单”）
AC3 未确认不执行
AC4 修改后的计划必须重新确认；取消是当前规划周期的终态，恢复规划必须由用户显式开始新周期
AC5 待确认与已确认 TestPlan 对会话调用方均为不可变值；调用方修改返回对象不得改变会话内部状态或已确认执行基线
AC6 确认前必须展示已解析的执行路径、选择原因及 XCUITest scheme/test plan（如适用）；多个可执行配置无法唯一确定时先询问用户，不得猜测
```

## E6 App 构建/安装/启动

### US-6.1 确定 App 来源（P0）

作为开发者，我不想手动准备包，希望 Agent 自动从当前 workspace 得到可安装 App。

验收标准：

```
AC1 默认 App 来源为当前 workspace（如某 iOS 项目的 .xcworkspace）
AC2 来源优先级：用户显式指定 .app/可解包 .ipa > 当前 workspace 中与 targetKind/destination 相容且可追溯的已有构建产物 > 自动 xcodebuild 构建
AC3 无既有产物时自动构建（识别 scheme/target/bundleId/签名）
AC4 无法确定时在 TUI 询问用户
AC5 用户体验上不需要先理解“App 安装来源”概念
AC6 用户指定 .ipa 时必须在 iTestAgent 管理的临时/产物目录受控解包，并唯一解析为 Payload/*.app；physical 安装前统一验证 .app 的 bundle 结构、目标平台/架构、bundleId 与签名可用性，不能只检查路径存在
```

### US-6.2 构建与安装到真机（P0）

作为开发者，我希望 Agent 构建并安装 App 到本机 iPhone。

验收标准：

```
AC1 使用 xcodebuild 构建，devicectl 安装
AC2 构建日志经 xcbeautify 可读化
AC3 签名失败时给出明确原因和修复建议，不静默失败
AC4 安装成功后可 launch/terminate/背景切换/deep link
AC5 DeviceBackend 探索路径在安装/执行前完成 App 与所选 backend 的 preflight；选择 Appium 时，WDA 已安装不等于 ready，必须通过路线对应的启动与 /status 或等价 WebDriver session 主动探测。XCUITest 路径不以 Appium/WDA ready 为前置，只校验已确认 scheme/test plan、destination、构建与签名
AC6 WDA 探测失败时明确区分未安装、签名/配置、launch、tunnel、/status 与 Appium session 失败；重签/重建/重装后必须重新探测，不能宣称无法证明的 profile 精确过期状态
AC7 重签、覆盖安装、重装或卸载任何设备 App 前必须经用户明确确认；免费账号三 App 上限不得触发自动卸载
```

### US-6.3 Simulator 构建安装（P0，ADR-011）

作为开发者，我希望 Agent 能将 App 构建为 Simulator SDK .app 并安装到指定 iOS Simulator。

验收标准：

```
AC1 使用 xcodebuild 构建 Simulator SDK .app（platform=iOS Simulator,id=<UDID>）
AC2 通过 simctl install/launch/terminate 管理 Simulator App 生命周期
AC3 BuildDriver 根据 targetKind 自动选择 destination（physical: platform=iOS,id=UDID / simulator: platform=iOS Simulator,id=UDID）
AC4 错误明确区分：构建失败 vs Simulator runtime 缺失 vs App slice 不匹配
AC5 不能将真机 .ipa 安装到 Simulator 或 Simulator .app 安装到真机
```

## E7 测试执行：XCUITest 路径

### US-7.1 执行已有 XCUITest（P0）

作为有可执行 UI 测试配置的开发者，我希望默认优先运行该 XCUITest 配置，并在执行前看到实际 scheme/test plan。

验收标准：

```text
Given 项目分析通过 metadata-only 读取获得 XCUITest 执行候选（scheme + Test action 中的 XCUITest target + 可选 test plan + 声明的 targetKind 相容性）
When 在 TestPlan 确认前解析执行路径
Then engine -> runner -> xcodebuild test -> xcresult -> parser -> report
AC1 确认前测试资产探测必须是 metadata-only，输出带 evidence/limitations 的结构候选及 available/none/indeterminate 状态；hasXCUITest 或 scheme 名称包含 test 不能单独证明候选成立，更不能宣称已真实可运行
AC2 用户显式 prefer=device_backend 时尊重显式选择；prefer=xcuitest 时必须唯一解析证据充分且相容的候选，否则 blocked，不得降级
AC3 prefer=auto 时，available 且唯一/明确默认候选选择 XCUITest；多个候选无法唯一确定时先询问；只有权威 status=none 才选择 DeviceBackend；indeterminate 必须 blocked
AC4 被选中的路径、scheme、可选 test plan 与选择原因在确认前展示并写入 TestPlan；执行前事实变化时 blocked 并要求重新确认，不得静默换路
AC5 结果解析使用 xcresultparser/xcparse
AC6 xcodebuild test 开始后的构建失败、测试失败、超时或解析失败保留为 XCUITest 路径结果，不自动转 DeviceBackend
AC7 确认前不得执行任何 Xcode build/test/archive action、scheme pre-action 或项目 Run Script；TestPlan 确认后，执行工程 build/test action 前必须通过 execute_project_build 权限；具体 destination、provisioning、App/test runner 安装或替换还必须通过 replace_device_app 权限
AC8 确认后的 metadata revalidation 只验证已选候选身份是否仍存在；任何 analyzer/readiness 异常必须返回带已选 path 与空 fallback history 的结构化 blocked/failed 结果，不得逸出 dispatcher 契约或改走其他路径
```

## E8 测试执行：DeviceBackend 探索路径

### US-8.1 DeviceBackend 探索执行（P0）

作为开发者，我希望在显式选择 DeviceBackend，或当前目标权威确认没有 XCUITest 候选时，让 Agent 在真机或 Simulator 上探索执行。

验收标准：

```text
Given 用户显式选择 DeviceBackend，或 prefer=auto 且 metadata-only 探测权威确认没有 XCUITest 执行候选
When 已确认 TestPlan 选择 DeviceBackend 探索
Then engine -> DeviceBackend -> UI actions -> run steps -> report；已确认步骤可另行固化为 Flow
AC1 通过可插拔 DeviceBackend 接口调用底层工具（如 Appium、mobile-mcp），不自研
AC2 对点击/输入/滑动/系统弹窗处理/截图/读取 UI tree 做 capability-aware 调度；backend 不支持或失败时显式 blocked/failed 并给出原因，不得假装成功
AC3 探索过程完整记录为 run steps；参与 case 判定的动作必须携带 caseId，并在该 case 动作后立即采集 checkpoint，不得用整轮结束后的最终页面冒充早期状态
AC4 元素定位不稳定时给出降级说明，不假装成功
AC5 不得因 XCUITest 构建、测试或解析失败在同一已确认执行中自动进入探索；跨路径重试必须修改或新建 TestPlan 并重新确认
AC6 自动探索在已确认 TestPlan 范围内执行低风险动作；R7 高风险动作仍逐项经过 PermissionEngine
AC7 普通导航与非敏感输入可在已确认 TestPlan 范围内执行；删除、支付、账号、安全设置、授权变更或语义不确定的敏感 UI 动作必须 fail-closed 并经过 PermissionEngine，不能仅按 tap/input 动词判为低风险
```

### US-8.2 交互式录制（P1）

作为开发者，我希望 Agent 建议下一步、我确认，逐步固化流程（人在环路）。

验收标准：

```
AC1 交互录制模式下 Agent 每步给出建议动作和依据，用户可确认、修改或跳过；该逐步确认要求不等同于 US-8.1 自动探索模式
AC2 只有用户确认且实际执行成功的步骤可固化为可重放 Flow；未确认建议、跳过步骤和失败定位不得进入可重放动作
AC3 探索式执行默认不保证可复现，只有固化成 Flow 后才可复现
AC4 保存、覆盖或写入项目目录中的 Flow 均需用户确认
```

## E9 iTestAgent Flow（录制与重放）

### US-9.1 记录 Run Steps（P0）

作为开发者，我希望每次执行都被结构化记录。

验收标准：

```
AC1 Level 1 Run Steps：结构化记录实际执行过程
AC2 每步至少含 stepId、sequence、backend、targetKind、动作类型、目标、输入、结果/状态、起始时间、耗时和证据引用
AC3 run 级 setup/teardown 步骤可无 caseId；参与 case 断言或 case 结果计算的步骤必须包含 caseId
AC4 Run Steps 是事实日志，不等同于 Flow；Flow 只能从已确认步骤编译
AC5 sequence 只对实际产生的 RunStep 从 1 严格递增；跳过建议、未执行建议或仅存在于录制 UI 的 RecordingStep 不占用 RunStep sequence
AC6 secret 输入只记录 SecretRef/脱敏占位符，不得把账号、OTP、token、支付或密码原文写入 RunStep 或 Flow
```

### US-9.2 可重放 Flow（P0）

作为开发者，我希望把过程保存为可重放 Flow。

验收标准：

```
AC1 Level 2 Replayable Flow：自研 iTestAgent Flow YAML
AC2 itestagent run flow <flowId> 默认执行真实重放；--validate-only 只做 schema/状态/目标/能力校验，不启动 backend 或产生设备副作用
AC3 Flow v2 至少含 schemaVersion/flowId/source/status/supportedTargetKinds/requiredCapabilities/lastValidatedTargets/steps；FlowStep 可选 caseId 用于保留录制时的 case 语义，该增量字段不提升 schemaVersion
AC4 Flow 默认存 ~/.itestagent/flows；写入项目 .itestagent/flows 需用户确认。未传 --project 时仅查找全局 Flow；传入 --project 时先查项目级再 fallback 全局，同 ID 时项目级胜出，命令必须输出实际来源
AC5 重放目标必须显式解析为 targetKind + device identity：可来自命令参数或交互式选择；不得从 supportedTargetKinds/lastValidatedTargets 的数组顺序猜测，跨 targetKind 不得静默 fallback
AC6 confirmed Flow 可重放；draft Flow 仅可在本次交互确认后重放且不自动改写状态，非交互模式必须 blocked；deprecated Flow 必须 blocked
AC7 BackendSelector 必须根据 targetKind、requiredCapabilities、显式偏好与 healthcheck 选择生产 DeviceBackend；requiredCapabilities 为可扩展字符串集合，canonical 名称为 appLifecycle/uiTree/screenshot/coordinateTap/swipe/textInput/pressButton/openUrl/video/logs/crashLogs/visualScreenshot/visualTap/location/push，必须从实际 steps 推导而非从 backend 名称推测；仅 comment/wait 的 Flow 可为空集合，未知能力必须 unsupported/fail-closed；能力或环境不足时输出结构化原因/修复建议，生产入口禁止切换 MockBackend/dry-run
AC8 重放必须经过 backend session/readiness 前置，并在成功、失败、blocked 或取消后执行同 owner 清理；清理失败必须作为结构化 infra failure 显式返回，且不得覆盖已产生的 replay step/evidence 事实；abort 语义遵循 ADR-010，已知全链路取消收口仍由 T6.10/DEF-029/DEF-033 验证
AC9 T6.7 必须输出真实且可关联的 replay step/evidence 事实（稳定 stepId/sequence/targetKind，有 case 语义时带 caseId）；证据不适用、未请求、不支持或采集失败必须显式记录，只有指向当前 run 隔离目录中普通且非空文件的证据才能生成 ArtifactRef，禁止空路径、目录路径或伪造 ArtifactRef；T6.7 在 T6.8 前可使用按 runId 隔离的本地 staging artifacts，统一 RunStore/steps.json/报告三件套持久化属于 T6.8
AC10 重放默认不改写 Flow 或 lastValidatedTargets；若用户要求回写验证记录，必须经过 overwrite_flow 确认
AC11 secret 只能通过内存值或 SecretRef 注入；screenshot/video/UI tree 原文必须按 ADR-032 作为 raw-local-only 证据，按 runId 隔离且目录/文件权限至少收紧为 0700/0600，不得标为 safe 或进入模型/报告正文/外传；typeText 的空字符串是无效 no-op，必须显式 blocked 而不得记为成功
```

## E13 证据采集

